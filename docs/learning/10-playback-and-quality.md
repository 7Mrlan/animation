# 第 10 章 让动画停得下来，也能稳定复用

能循环只是动画的一部分。用户滚走了，页面切到后台了，或者只想看一张静态图时，组件也需要给出合理的结果。移植本项目之前，先读这一章，能少漏几段看不见却很有用的代码。

源码入口是 [useMotionActivity.ts](../../src/hooks/useMotionActivity.ts)、[viewport-window.ts](../../src/lib/viewport-window.ts)、[AnimationCard.tsx](../../src/components/AnimationCard.tsx) 和 [styles.css](../../src/styles.css)。

## 场景窗口与播放条件

Hook 返回的 `active` 按下面的表达式计算。

```ts
mounted && inView && pageVisible && !paused && !reduced
```

`mounted` 表示动画场景是否已经挂载在预加载窗口内，`inView` 来自内部舞台的 IntersectionObserver，`pageVisible` 跟随 `document.hidden`，`paused` 汇总手动暂停状态，`reduced` 来自系统媒体查询。只要有一项不允许播放，就停止主要动画。

显现和播放使用两个不同的观察器：显现观察整张卡片，阈值是 `0`，卡片露出一点就淡入，避免“标题已经可见但整张卡片还是透明”的状态；播放观察内部舞台，阈值是 `0.08`，减少边缘卡片不必要的动画帧。两个回调里实际保存的都是 `entry.isIntersecting`，阈值用于安排交叉状态通知，当前代码没有直接判断 `intersectionRatio >= 0.08`。因此不要把它解释为严格的“只有露出超过 8% 才播放”。若产品需要严格比例，要把这个条件明确写进判断。可参照 [MDN Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API)。

这些 Hook 直接访问浏览器对象，适用于当前 Vite 客户端页面。复制进有服务端渲染的项目时，需要检查初始化阶段能否访问 `document`、`matchMedia` 和 `IntersectionObserver`。

## 为什么只挂载视口附近的场景

每张卡片的外壳（标题、说明、源码按钮、锚点）始终留在 DOM 里，只有动画场景在窗口外被卸载。`catalog.tsx` 里每个 `Scene` 都是 `React.lazy` 分块，所以挂载窗口同时也是加载窗口：卡片进入预加载区才会请求对应的 JS 和 CSS。

这样做的原因是：

- 动画场景才是“贵”的部分：大量元素、RAF、Lottie 实例和合成层。卡片文字本身很轻。
- 网格高度、滚动位置、`#deck` 之类的深链接和键盘顺序依赖卡片外壳。把整张卡片虚拟化会破坏这些能力，也会让查找和锚点失效。
- 预加载边界是 600px，释放边界是 1000px。两个边界分开，停在边界附近时不会反复挂载/卸载。状态机在 `reduceSceneWindow` 里，测试覆盖了边界和一次性显现。
- 所有卡片共用按配置分组的观察器，稳定运行时只保留 4 个 IntersectionObserver（预加载、释放、显现、播放），而不是每张卡片各建 4 个。注册表在 `observer-registry.ts`，单元测试覆盖共享、多订阅、清理和分组重建；外壳层的页面可见性、减少动态效果各只有一份共享订阅（DuoPlayer 仍会为自己的播放器监听标签页切换）。
- 分块加载用 `Suspense` 的静态占位遮住等待时间；单个分块失败由卡片级错误边界兜底，只显示 `SCENE / UNAVAILABLE`，不会让整页白屏。

卸载后场景内部状态会丢失：CardDeck 的时间轴、Duo 的播放器、DeepSeek 的拖动位置都会在重新进入预加载区时重建。代码分块会被浏览器缓存，但播放器实例和运动时钟会从头开始。这是窗口化的取舍；卡片外壳层面的暂停状态、筛选和源码面板不受影响。重播仍然通过改变 `key` 重建场景，和窗口化卸载走的是同一条清理路径。

## 滚动显现为什么不撑高页面

显现使用 `translate`、`scale` 和 `opacity`，它们不参与布局。但**正向 `translate` 会影响可滚动溢出区域**：如果页脚在未显现时向下平移 20px，文档的 `scrollHeight` 会多出 20px，显现结束时再缩回去，底部就会跳一下。

因此卡片使用 `translate: 0 26px`（下方始终还有学习说明和页脚，溢出不会改变文档高度）；内容更靠下的学习说明和页脚只用 `opacity + scale`，不产生向下的溢出。浏览器验收时可以在页面顶部和底部分别读取 `document.documentElement.scrollHeight`，两者应该一致。

显现只记录一次：滚出视口后卡片不会重新隐藏，避免上下滚动时闪烁。键盘聚焦通过 `onFocusCapture` 提前显现，`prefers-reduced-motion` 下则直接显示、关闭过渡。

深链接也有同样的位移问题：`scrollIntoView` 按当前的变换后矩形对齐，如果卡片仍在 26px 的显现位移中，最终会偏上。`App` 改为累加 `offsetTop` 得到布局位置再滚动；`:target` 规则则让文档加载后命中的目标直接落到终态。两者都不依赖过渡何时结束。

## CSS、RAF 与 Lottie 分别怎么停

| 动画类型   | 当前暂停方式                                                     | 清理位置                   |
| ---------- | ---------------------------------------------------------------- | -------------------------- |
| 场景窗口   | 离开 1000px 释放边界后卸载整个场景；附近时重新挂载并按需加载分块 | `useMotionActivity` 订阅   |
| CSS 循环   | 外壳设置 `data-paused`，匹配 `animation-play-state`；远处卸载    | 样式随 DOM 移除            |
| 卡片时间轴 | `active` 改变后取消 RAF，不再预约后续帧                          | `CardDeck` 的 Effect 清理  |
| Lottie     | `visible` 改变后调用 `pause()`；远处卸载时 `destroy()`           | `DuoPlayer` 的 Effect 清理 |
| 指针驱动   | 暂停时外壳关闭指针命中，组件卸载时取消待执行 RAF                 | 各指针组件的清理函数       |

CSS 规则同时覆盖普通元素与 `::before`、`::after`。漏掉伪元素，会出现主体停了而轨道还在移动的现象。

这套暂停主要处理动画循环。已有 CSS transition 可能还会走完，刚预约的指针更新也可能完成最后一次写入。若要求暂停瞬间所有像素都绝对冻结，需要更严格的状态控制，不能仅靠当前外壳声明。

## 重播和窗口卸载都会重建场景

`AnimationCard` 用 `revision` 作为 `.scene-root` 的 key。点击重播后，旧子树被卸载，新子树重新创建。CSS 动画回到起点，CardDeck 的内部 ref 重新初始化，Lottie 也会重新走加载流程。

窗口化卸载也会走同一条清理路径：RAF 被取消、Lottie 被销毁、事件监听被移除。区别是重播由用户触发，窗口卸载由滚动位置触发；两者都不需要为每种动画写单独的“卸载”分支。

这种做法简单，适合目前这些小型演示。它也会重建 DOM 和播放器实例。如果以后载入较大的动画，可以考虑调用播放器的定位接口，并为不同类型提供单独的重播方法。Duo 的 JSON 已经在模块级缓存（失败时会清空以便重试），窗口反复挂载不会重复请求；但 Lottie 播放器实例仍会重建。是否继续优化，要看实际初始化成本。

筛选掉卡片同样会卸载组件。把 RAF、监听器和请求清理放在组件生命周期内，比依赖页面永远不切换更稳妥。

## 减少动态效果仍要能看见内容

`useReducedMotion` 既读取初始偏好，也监听后续变更。静态模式下，外壳移除循环与过渡，Duo 显示海报。CardDeck 允许交互触发一次静态姿态更新，但不再持续预约动画帧。

测试时不要只看“有没有停止”。还要检查元素是否留在透明初态、内容有没有被移到容器外，以及键盘能否操作仍然需要的控件。Gemini 的公共视觉容器保持首帧可见，就是为这种情况留出的静态状态。

## 卡片质感从哪几层来

`.animation-card` 是白色外框，内部 `.stage` 才是有颜色的动画舞台。外框有几层低透明度阴影，舞台另有内侧阴影和边缘高光。两部分分开，动画的颜色不会淹没标题和说明。

悬停抬升发生在外卡片，动画内部的运动发生在各自元素上。这减少了它们争写 transform 的机会。舞台设置 `overflow: hidden`，运动元素超出范围后被裁切；如果改大浮动幅度，要再看一遍边缘。

想要更清晰的质感，先检查留白、边缘和对比度，再改阴影。提示词可以给出“外卡片抬升不超过 3px，主体图形保持原尺寸”这样的范围，减少 AI 把整张页面都改掉的机会。

## 用检查回答具体问题

`npm run check` 会执行类型检查、现有测试和生产构建。这能发现类型错误、打包失败，以及已覆盖的卡片几何问题。它不会替你确认手机点击、图形裁切或不同设备的流畅程度。

| 要确认的事情                   | 合适的检查                                          |
| ------------------------------ | --------------------------------------------------- |
| 卡片首尾位置是否连续           | 时间轴纯函数测试                                    |
| 窗口边界会不会反复挂载         | `viewport-window` 状态机测试 + 浏览器滚动观察       |
| 观察器是否共享、清理是否干净   | `observer-registry` 单元测试                        |
| 动画代码/CSS 是否按需加载      | 构建分块列表 + 浏览器网络面板                       |
| 页面底部会不会跳动             | 顶部/底部读取 `scrollHeight`，比较未显现/已显现状态 |
| 减少动态效果后是否仍能看到主体 | 浏览器开启相应媒体偏好                              |
| 多次筛选后是否积累播放器       | 浏览器观察 DOM、性能与生命周期                      |
| 源码弹窗能否关闭并返回触发按钮 | 键盘打开、Esc 关闭，再看焦点                        |
| 页面有无横向溢出               | 窄视口检查滚动宽度和元素矩形                        |
| 真实设备上是否卡顿             | 在目标设备录制性能轨迹，再定位瓶颈                  |

只在证据需要时增加测试。改一处颜色通常做构建和目视检查就够；改时间轴分界、层级或生命周期，才更需要相应的回归检查。

```text
请审查当前动画项目的播放生命周期，先不要修改文件。
阅读 useMotionActivity.ts、viewport-window.ts、observer-registry.ts、catalog.tsx、AnimationCard.tsx、CardDeck.tsx、DuoPlayer.tsx 和相关暂停/显现样式。
逐项核对手动暂停、离屏窗口、代码分块与 Suspense 回退、标签页隐藏、减少动态效果、重播、筛选卸载、滚动显现和键盘聚焦。
特别检查：视口边界抖动、窗口卸载导致的状态丢失、共享观察器的订阅/清理、分块加载失败是否拖垮整页、显现是否改变 scrollHeight、减少动态效果下是否仍能看到并操作内容。
每个结论都给出文件与实际分支，区分已有行为、潜在限制和已经复现的问题。
不要承诺固定帧率，也不要把 npm run check 等同于浏览器验收。
最后只提出最值得先处理的一项改动，写清复现步骤和验收方法。
```

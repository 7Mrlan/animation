# 第 12 章 写出 AI 能执行的动画任务

一条好用的提示词，要让 AI 找到正确代码，并让你能判断结果。文件范围、动作数值和验收方式写清以后，剩下的实现细节可以交给它处理。

本章提供八个任务模板，九个动画章节末尾也有对应的练习提示词。加上基础练习和审查示例，全册共有二十段可复制的提示词。模板默认在本仓库根目录使用，先替换尖括号中的内容，再提交给 AI。

## 先补齐一条需求

假设你想让代码终端“安静一点”。这个表达还没有指定要改速度、幅度还是颜色。先选终端位移幅度，再补上目标值，就能形成一个很小的任务。

```text
请阅读 src/animations/CodeWorkspace.tsx 和 CodeWorkspace.css。
把终端跟随指针的最大水平与垂直位移从 8px 降到 4px。
保留光圈和准星的完整跟随、坐标夹取、RAF 合帧，以及 5.6s 自动浮动。
只改这个动画所需的文件，不新增依赖。
验证指针在中心、四角和离开后的表现，运行 npm run build。
最后列出实际改动数值和验证结果；没做的检查要明确写出。
```

这段要求让 AI 有了具体入口。中心和四角提供输入，±4px 提供输出范围，离开后回中又补上结束状态。它无需猜测“安静”意味着整张画面都变灰，或把所有动画一并减速。

## 模板一 先讲解源码

适合你还没看懂实现，也不希望 AI 直接重写组件的时候。

```text
请讲解本项目中的 <组件名称>，先阅读 <TSX 路径>、<CSS 路径> 及其直接依赖。
本轮只讲解，不修改文件。
先按一次完整动作的先后顺序说明发生了什么，再对应到 DOM、状态、关键帧或时间轴。
列出控制幅度、周期和延迟的实际参数，说明百分比的参考对象。
区分当前已实现的行为与建议新增的行为，不用组件名猜实现。
挑一个初学者最容易改错的位置，说明可见症状和原因。
最后给一个只改一项参数的练习，以及判断练习完成的方法。
```

检查它是否给出了真实选择器或函数。只解释“这个组件让页面更有活力”，还没有完成任务。

## 模板二 修改一个明确效果

适合改浮动幅度、轮转停留或一组透明度。范围越小，越容易比较前后差别。

```text
请在 <组件与样式路径> 中完成下面这个局部修改。
当前行为为 <写实际状态或数值>，目标行为为 <写具体动作与目标数值>。
先确认控制这段效果的代码，再修改直接相关的文件。
保留 <列出两项最容易被误改的行为>，不改其他卡片和页面布局。
若同一属性同时被关键帧、内联样式或 hover 控制，先解释它们的关系。
验收时检查 <初始状态>、<交互中的状态>、<结束状态>，以及减少动态效果。
执行与改动相称的检查，并报告修改文件、结果和未验证项。
```

不要在一个局部任务中同时要求重构整个动画系统。若发现公共结构确实需要调整，让 AI 先说明受影响的范围，再决定是否纳入本次修改。

## 模板三 新增一张动画卡片

这个模板允许 AI 从头实现，但要求它沿用当前目录与播放约定。示例目标是一张不使用品牌素材的纸片动画。

```text
请先阅读 src/catalog.tsx、AnimationCard.tsx、useMotionActivity.ts，以及 FloatingMail 的组件和 CSS。
新增一张独立纸片动画卡，命名为 <名称>。
画面包含 <两个或三个可描述的图形>；主体上下浮动 4px，周期 6s，首尾姿态相同。
若有指针交互，最大位移不超过 6px；触摸设备没有悬停时仍能正常观看。
沿用现有 React、TypeScript 和普通 CSS，不引入动画库或远程素材。
在 src/animations 新建组件及样式，并在 catalog 中登记说明和源码路径。
接入暂停、重播、离屏和减少动态效果；若使用 JS 回调，要补齐卸载清理。
检查窄屏、键盘操作和源码面板，运行 npm run check。
说明新增文件与复用方式，避免改动已有动画的视觉行为。
```

这里将必要的接入点写进要求，能减少“动画做好了，但页面找不到”或“暂停按钮只对旧卡片有效”的遗漏。

## 模板四 根据复现步骤排错

先给 AI 能重复操作的过程。浏览器名称、视口、系统动态偏好和控制台错误都可以提供线索，填实际信息即可。

```text
请排查 <组件名称> 的 <可见问题>。
复现环境为 <浏览器与视口>，减少动态效果为 <开启或关闭>。
操作过程为 <按顺序写具体动作>。
期望结果为 <可观察结果>，实际结果为 <可观察结果>。
相关文件为 <已知路径>，已有报错为 <原始错误或无报错>。
先沿输入、状态、DOM/CSS 的顺序定位原因，再做最小修复。
不要用任意延迟隐藏问题，不修改无关样式。
增加能覆盖根因的检查；如果适合自动测试就补测试，否则给出明确的手动回归步骤。
最后说明根因、修改位置以及复现是否消失，不宣称未执行的检查已通过。
```

“偶尔不对”很难验证。可以改写成“暂停后切到 CSS 循环分类，某张卡片的主体不可见；恢复播放后才出现”。这样 AI 能追踪挂载初态和暂停样式，而不是到处修改透明度。

## 模板五 按证据处理性能

当你已经观察到卡顿，使用这份模板。还没有复现时，不必提前加入缓存和大量 `will-change`。

```text
请调查 <页面或组件> 在 <设备、视口、操作> 下的卡顿。
先复现并记录性能证据，区分 React 更新、布局、绘制与动画回调的开销。
记录可复现的基线，不把 RAF 或 transform 直接视为性能已优化的证明。
优先处理耗时最明确的一处，保持动作路径、速度和交互含义。
如果无法获取性能轨迹，请改为源码审查，明确结论属于假设。
检查离屏与后台状态是否继续消耗资源，以及反复挂载是否残留监听或实例。
提交前后同条件的比较、修改范围和可能的取舍，不承诺所有设备固定帧率。
```

比较要使用相同的页面内容和操作。如果修改前在桌面测，修改后在手机测，两组数字无法直接证明改动有效。

## 模板六 提取为可复用组件

适合把当前项目中的动画带到另一处。先列清所需能力，能减少复制时漏掉样式或播放器。

```text
请把 <动画名称> 整理成可复用组件，先阅读它的组件、CSS、素材和播放控制依赖。
需要公开的参数为 <参数名称、单位、默认值>。
保持默认参数下的现有画面，说明仍然固定的条件，例如卡片数量或比例。
组件需要支持 <客户端页面或含 SSR 的目标环境>，按实际环境处理浏览器对象访问。
给出最小调用示例、容器尺寸要求和所有必须复制的文件。
保留实例隔离、减少动态效果与卸载清理，不新增远程请求。
验证默认值、一个较小值和一个边缘值，运行相应类型与构建检查。
报告兼容范围，不把尚未验证的环境列为已支持。
```

参数名称也值得检查。`maxShift` 配合 px 单位，比让调用方传入难以理解的换算系数更清楚。默认值应能保留当前展示结果，方便比较。

## 模板七 给下一轮 AI 留下上下文

同一改动需要跨几轮处理时，用短记录保存当前事实。不要把整段聊天原样复制给下一个任务。

```text
请根据当前工作区写一份交接说明，本轮不再修改代码。
包含任务目标、已改文件、关键参数、执行过的命令和实际结果。
列出仍然存在的问题、可靠的复现步骤以及下一步最小动作。
区分已提交和未提交内容，不猜测其他人的修改意图。
附上相关源码路径，注明哪些判断需要浏览器继续验证。
不要把密钥、环境变量值或无关日志写入说明。
```

保留“执行过什么”和“结果怎样”即可。将未执行的计划写成已完成，会让下一轮跳过本来需要的检查。

## 模板八 让文档跟着代码更新

用于动画改动完成以后。它让文档说明实际实现，也保留教学中有用的计算过程。

```text
请对照当前源码更新 <章节路径>，先读取本次改动和对应组件。
核对 DOM 结构、关键帧、参数单位、时间轴分界和播放条件。
将已经实现的行为写成事实，将未实现的想法放入明确标注的练习。
保留可计算的例子，删掉重复解释和没有证据的性能结论。
更新章节提示词，使文件路径、默认值和验收条件与新版本一致。
检查相对链接和代码片段，正文用清楚的中文解释，不编造亲测经历。
只修改相关文档，最后说明文档变化与仍待确认的部分。
```

## 提交给 AI 前花一分钟检查

把提示词中的对象和数值单独读一遍。若你自己也不知道哪个图形需要移动、它该移动多远，先回到画面观察。然后确认文件范围和验收条件没有互相矛盾。

当 AI 返回改动后，先看 diff，再运行对应检查。比较的重点是要求有没有落实，以及其他动画是否受到影响。修改范围、执行证据和可见结果都能对应起来，这次任务才方便继续维护。
